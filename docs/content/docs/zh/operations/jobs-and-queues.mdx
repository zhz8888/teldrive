## Worker

默认配置：

```yaml
jobs:
  run-workers: true
```

仅 API 的实例：

```yaml
jobs:
  run-workers: false
```

共享同一数据库的进程中，至少要有一个运行 worker。禁用 worker 的实例会构建任务运行时，但从不启动它，也从不注册周期调度。

## 运行的内容

| 类型 | 队列 | 运行时机 |
| --- | --- | --- |
| 上传/会话清理 | `maintenance` | 周期执行 |
| 用户事件清理 | `maintenance` | 周期执行 |
| 回收站清理 | `maintenance` | 周期执行 |
| 待删除文件清除 | `maintenance` | 周期执行 |
| 孤立 Telegram 分片清理 | `maintenance` | 周期执行 |
| bot 开通 | `maintenance` | 按需（bot 验证时） |
| 后台导入批次 | `uploads` | 按需 |
| 按文件的后台导入 | `uploads` | 按需 |

这些周期调度在第一个启用 worker 的进程启动时创建。重启时它们**不会**被重新创建，因此你的修改能在升级后保留下来；并且所有 cron 表达式都按 **UTC** 求值，与主机时钟无关：

| 调度 | 频率 | 删除内容 |
| --- | --- | --- |
| 回收站清理 | 每 12 小时 | 超过 30 天的回收站文件 |
| 待删除文件清除 | 每 12 小时 | 已标记为待删除的文件 |
| 上传/会话清理 | 每 12 小时 | 已过期的上传会话及其分片 |
| 用户事件清理 | 每天午夜 | 超过 48 小时、可重放的事件，以及已过期的 Telegram 登录流程 |
| 孤立 Telegram 分片清理 | 每 14 天 | 没有任何文件或上传分片引用的 Telegram 文档 |

保留时间窗口写在**周期任务参数**中，而不是配置里 —— 请在**设置 → 周期任务**中修改。

## 任务界面

使用**任务**页面查看后台任务、查看详情、重试和取消。

任务状态只有这些：`pending`、`scheduled`、`available`、`running`、`retryable`、`completed`、`discarded`、`cancelled`。并不存在 `failed` 状态 —— 仍有余量尝试次数的任务是 **`retryable`**，用尽尝试次数的任务则是 **`discarded`**。`cancelled`、`discarded` 和 `retryable` 状态会提供重试；`pending`、`scheduled`、`available`、`running` 和 `retryable` 状态会提供取消。

瞬时失败请在查明原因之后再重试 —— 任务详情页会展示每一次尝试及其错误和时间戳。不再需要的工作请予以取消；取消只会停止后续处理，不会撤销已经完成的外部副作用。

任务记录会不断累积，除非你主动删除。`DELETE /v1/jobs/{jobId}` 删除单个任务，`DELETE /v1/jobs/purge?status=completed` 按状态批量清除（也接受 `retryable` 或 `discarded`）。只有终态状态会被接受；非终态状态会返回 `409` 拒绝。清除只会删除任务记录，绝不会撤销它们已经完成的工作 —— 删除一个导入任务不会删除它所导入的文件。

## 队列控制

队列可以暂停/恢复以便维护。暂停的队列会停止分发新工作；已排队的任务仍留在队列中，并在恢复时从原处继续。暂停时已经**正在运行**的任务不会被中断。

该操作需要管理员或所有者角色。其他用户会收到 `403 administrator access is required`，并且队列列表会被过滤为仅包含他们自己任务所在的队列，而不是被直接拒绝 —— 因此非管理员看起来可能会“缺少”`maintenance` 队列。

## 周期任务

使用**设置 → 周期任务**创建、更新、暂停、恢复、重置或删除已调度的任务。这些操作都需要管理员或所有者角色；普通用户看不到该页面。

`reset` 会恢复出厂的默认调度，并**一次性丢弃运维人员对所有周期任务所做的修改**。如果你只想改其中一个，请改为单独暂停或编辑对应的调度。

## 重启 worker

关闭时 Teldrive 会停止分发新任务，并等待执行中的任务结束，上限为 River 的**30 秒软停止**。这段等待受 `http.shutdown-timeout` 限制，该值默认为 **10 秒** —— 因此在出厂默认配置下，执行中的任务会在 10 秒后被取消。在依赖优雅重启之前请先提高它：

```yaml
http:
  shutdown-timeout: 40s
```

被中断的任务不会丢失：可重试的工作会重新回到队列，导入 worker 会从匹配到的未完成上传会话处继续，而不是从头重新处理该文件。请始终发送 `SIGTERM`，让进程自行排空。

## 多实例

Worker 容量是**每个启用 worker 的进程、每个队列并发 2 个任务**，而不是一个无上限的连接池。每个队列的总任务并发数为 2 × 启用 worker 的进程数，因此每增加一个进程，容量就按 2 的步进增加。

这两个队列被刻意分开，以免长时间的孤立分片清理饿死导入；如果上传堆积而 `maintenance` 却空闲，瓶颈在 worker 进程数，而不在调度器。

增加 worker 时，请监控 PostgreSQL 总连接数、Telegram 错误、资源占用、队列深度和重试情况。

参见[多实例部署](/advanced/multi-instance)。
