## Workers

Default:

```yaml
jobs:
  run-workers: true
```

API-only instance:

```yaml
jobs:
  run-workers: false
```

At least one process sharing the database must run workers. An instance with workers disabled builds the job runtime but never starts it, and never registers the periodic schedules.

## What runs

| Kind | Queue | Runs when |
| --- | --- | --- |
| Upload/session cleanup | `maintenance` | periodic |
| User-event cleanup | `maintenance` | periodic |
| Trash cleanup | `maintenance` | periodic |
| Pending-file purge | `maintenance` | periodic |
| Orphaned Telegram part cleanup | `maintenance` | periodic |
| Bot provisioning | `maintenance` | on demand (bot verification) |
| Background import batch | `uploads` | on demand |
| Per-file background import | `uploads` | on demand |

The periodic schedules are created the first time a worker-enabled process starts. They are **not** recreated on restart, so your edits survive an upgrade, and all cron expressions are evaluated in **UTC** regardless of the host clock:

| Schedule | Cadence | What it deletes |
| --- | --- | --- |
| Trash cleanup | every 12h | trashed files older than 30 days |
| Pending-file purge | every 12h | files already marked deletion-pending |
| Upload/session cleanup | every 12h | expired upload sessions and their parts |
| User-event cleanup | daily at midnight | replayable events older than 48h, plus expired Telegram login flows |
| Orphaned Telegram part cleanup | every 14 days | Telegram documents no file or upload part references |

The retention windows live in the **periodic job arguments**, not in configuration — edit them from **Settings → Periodic jobs**.

## Tasks UI

Use **Tasks** to inspect background jobs, view details, retry, and cancel.

Job states are exactly: `pending`, `scheduled`, `available`, `running`, `retryable`, `completed`, `discarded`, `cancelled`. There is no `failed` state — a job that still has attempts left is **`retryable`**, and one that exhausted its attempts is **`discarded`**. Retry is offered for `cancelled`, `discarded` and `retryable`; cancel is offered for `pending`, `scheduled`, `available`, `running` and `retryable`.

Retry transient failures only after checking the cause — the task detail view shows every attempt with its error and timestamp. Cancel work that is no longer wanted; cancellation stops future processing and does not undo external side effects that already completed.

Task rows accumulate forever unless you remove them. `DELETE /v1/jobs/{jobId}` deletes one job and `DELETE /v1/jobs/purge?status=completed` purges by status (`retryable` or `discarded` also accepted). Only final states are accepted; a non-final state is rejected with `409`. Purging removes the task records, never the work they did — deleting an import task does not delete the files it imported.

## Queue controls

Queues can be paused/resumed for maintenance. A paused queue stops handing out new work; queued jobs stay queued and resume where they left off. A job already **running** when you pause is not interrupted.

This requires the admin or owner role. Other users get `403 administrator access is required`, and the queue list is filtered to the queues holding their own jobs rather than refused — so a non-admin may appear to be missing the `maintenance` queue.

## Periodic jobs

Use **Settings → Periodic jobs** to create, update, pause, resume, reset, or delete scheduled jobs. All of these require the admin or owner role; the page is not shown to ordinary users.

`reset` restores the shipped default schedules and **discards any operator edits** to all periodic jobs at once. Pause or edit individual schedules instead when you only mean to change one.

## Restarting workers

On shutdown Teldrive stops handing out new jobs and waits for in-flight ones, up to River's **30-second soft stop**. That wait is bounded by `http.shutdown-timeout`, which defaults to **10 seconds** — so with shipped defaults in-flight jobs are cancelled after 10s. Raise it before relying on graceful restarts:

```yaml
http:
  shutdown-timeout: 40s
```

Interrupted jobs are not lost: retryable work returns to the queue, and import workers resume from a matching open upload session rather than starting the file over. Always send `SIGTERM` and let the process drain.

## Multi-instance

Worker capacity is **two concurrent jobs per queue per worker-enabled process**, not an unbounded pool. Total job concurrency is `2 × (worker-enabled processes)` per queue, so adding processes moves capacity in steps of two.

The two queues are deliberately separate so a long orphan sweep cannot starve imports; if uploads back up while `maintenance` is idle, the constraint is worker processes, not the scheduler.

When adding workers, monitor aggregate PostgreSQL connections, Telegram errors, resource use, queue depth, and retries.

See [Multi-instance deployments](/advanced/multi-instance).
