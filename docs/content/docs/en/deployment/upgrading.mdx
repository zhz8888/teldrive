---
title: Upgrading
description: Upgrade Teldrive with a database backup, validation, smoke tests, and rollback path.
---

Startup applies migrations before it serves anything, and every instance applies them: the TelDrive schema migrations, then the River migration line, then the RiverPro line. All three land in `database.schema` (default `teldrive`), which also holds the River job tables. Back up PostgreSQL before the new version initializes — for a multi-replica rollout, run one `teldrive check` first so only one process is migrating.

## Before upgrading

1. Read release notes.
2. Record the current version.
3. Back up PostgreSQL.
4. Verify you still have `security.data-key` and content-encryption keys.
5. Keep the previous image/binary available.

Use a pinned release tag:

```yaml
image: ghcr.io/zhz8888/teldrive:vX.Y.Z
```

## Compose

```bash
docker compose pull teldrive
docker compose run --rm teldrive check
docker compose up -d teldrive
docker compose logs --tail=250 teldrive
```

`check` applies every migration before it exits, so the backup must exist before it runs.

**Upgrading from Teldrive v1 is different.** `database.auto-migrate-legacy` defaults to `true`, so on a database still carrying the v1 schema the first `check` — or the first `run` — performs the v1→v2 conversion, not a routine migration. It takes an advisory lock, builds a staging schema, converts the v1 rows forward into it, and renames schemas inside a single transaction; the original v1 schema is **additionally retained** under `teldrive_legacy_backup_<timestamp>` as a rollback copy. Read [Migrate from Teldrive v1](/deployment/v1-migration) before running either command against a v1 database.

## Binary install

Keep old and new binaries side by side:

```text
/usr/local/lib/teldrive/teldrive-vOLD
/usr/local/lib/teldrive/teldrive-vX.Y.Z
```

Validate before switching:

```bash
/usr/local/lib/teldrive/teldrive-vX.Y.Z check --config /etc/teldrive/config.toml
```

## Smoke test

Verify:

- `/health/ready` for load-balancer routing (503 when the database ping fails);
- `/health/live` only to confirm the process itself came up — it stays `200` while PostgreSQL is down, so it must not be the readiness probe;
- login/session refresh;
- listing, upload, download, rename/move/trash/restore;
- tasks;
- shares and bots if used.

## Rollback

An older binary may not work against a newer migrated schema. A full rollback may require:

1. stop the new version;
2. restore the pre-upgrade PostgreSQL backup;
3. restore the previous binary/image and matching configuration;
4. run `teldrive check` before serving traffic.

For multi-instance deployments, coordinate the rollout and avoid unsupported mixed-version operation.

See [Backup and restore](/deployment/backup-and-restore).
