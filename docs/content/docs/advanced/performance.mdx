title: Performance tuning
description: Tune Telegram concurrency, hashing, PostgreSQL, HTTP streaming, and memory use.
---

Measure before changing concurrency.

## Baseline

Record:

- upload/download throughput;
- CPU and memory;
- PostgreSQL connections;
- Telegram retry/rate-limit errors;
- proxy timeouts/errors.

## Uploads

```yaml
telegram:
  upload-threads: 8
```

Valid range: `1`–`32`. Increase gradually and stop when throughput no longer improves or errors/resource use rise.

Hashing can also consume CPU:

```yaml
uploads:
  hashing-enabled: true
```

Disable it only if measurements show it is the bottleneck and you do not need server-computed hashes.

## Downloads

```yaml
telegram:
  download-read-buffers: 32
  download-read-parallel: 4
  download-bots: 0
```

`download-read-parallel` controls concurrent chunk fetches per stream. `download-read-buffers` controls prefetched chunks in memory. Both multiply across simultaneous downloads.

Use bots only after normal user-client downloads work correctly.

## PostgreSQL

```yaml
database:
  max-connections: 25
  min-connections: 2
```

Increase the pool only when requests are waiting for connections and PostgreSQL has capacity. With multiple Teldrive instances, budget the sum of every process pool.

## Memory cache

```yaml
cache:
  memory:
    size: 5MB
```

This is metadata/application cache, not file-content cache.

## Timeouts

```yaml
http:
  read-timeout: 1h
  write-timeout: 1h
```

If transfers fail at a consistent duration, check the shortest timeout across the client, CDN/load balancer, reverse proxy, and Teldrive.

## Telegram rate limiting

Keep client-side rate limiting enabled unless you have a specific reason to change it:

```yaml
telegram:
  rate-limit: true
  rate-interval: 50ms
  rate-burst: 10
```

## Small hosts

A host with one core and a gigabyte of memory is enough to run the server, as long as the memory-hungry settings are not left at their defaults. The numbers below assume PostgreSQL runs elsewhere; if it shares the box, subtract its footprint from the budget as well.

Memory is spent almost entirely on downloads. Each open range buffers `telegram.download-read-buffers` megabytes of prefetched Telegram chunks, so the memory ceiling is that number multiplied by `uploads.max-concurrent-downloads`. Uploads are streamed and encrypt in 64 KiB pooled blocks, so they cost little by comparison.

```yaml
telegram:
  upload-threads: 2
  download-read-buffers: 8
  download-read-parallel: 2

uploads:
  max-concurrent-downloads: 2

database:
  max-connections: 10

cache:
  memory:
    size: 2MB
```

That is 16 MiB of download buffers at the default limit, where the defaults would have allowed 128 MiB with no ceiling on the number of streams.

Give the Go runtime a memory ceiling so the collector reacts before the kernel does. Without one the collector waits until the heap has doubled, which on a small host is often after the kernel has started reclaiming:

```bash
GOMEMLIMIT=384MiB teldrive run
```

The runtime reads this variable itself at startup, so no configuration key is needed and **no code should be added to read or apply it**: doing so would duplicate the runtime, and `runtime/debug.SetMemoryLimit(-1)` is a no-op on current Go, so an "off" branch written that way would silently fail. `off` removes the ceiling. Leave the variable unset on a host with headroom.

Hashing is the first thing to give up when a single core cannot keep up, at the cost of storing parts with no checksum:

```yaml
uploads:
  hashing-enabled: false
```

## Tuning order

1. Fix proxy/time-out errors.
2. Measure one upload and one download.
3. Check CPU, memory, and network saturation.
4. Adjust upload or download concurrency one setting at a time.
5. Re-test under realistic simultaneous load.
6. Check PostgreSQL pool pressure.
7. Consider bots or horizontal scaling last.
